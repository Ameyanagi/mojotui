# MojoTUI v0.1 execution plan

This document turns the open work in [PLAN.md](../PLAN.md) into issue-sized
tasks for the first public source release. `PLAN.md` remains the product and
architecture roadmap; this file owns execution order, dependencies, gates, and
handoffs.

## Release contract

The working release target is `v0.1.0` because `pixi.toml` is versioned
`0.1.0`, the repository has no tags, and `CHANGELOG.md` says no public release
has been published. The historical `0.1` through `0.8` entries in `PLAN.md`
described capability increments, not shipped artifacts. MTUI-001 reconciles
that history with the first public release below.

The release contains the already implemented renderer, terminal backends,
widgets, application host, editor, forms, capability model, and editor example.
It also completes the Stage I extension foundation required for another Mojo
project to consume and extend the library without private imports. Stage J
widget expansion and performance work begins after `v0.1.0`.

The release is source-first and pins Mojo `1.1.0.dev2026081813`. A package
artifact may be published only when its recipe passes an installed-consumer
test against that exact compiler on every supported target.

The publication job uses the protected GitHub `release` environment. Before
MTUI-305, repository settings must retain at least one designated maintainer as
a required reviewer. That reviewer approves publication only after verifying
that the annotated or signed tag peels to the approved release-candidate commit;
an unprotected environment blocks the release gate.

## Audited baseline

Audit date: 2026-08-20, commit `aae65ad` on `agent/editor-example`.

- `pixi run --locked check` passes locally on macOS ARM64.
- The suite contains 217 test functions in 29 Mojo test modules and 20
  compile-fail fixtures.
- PTY coverage passes normal close, implicit cleanup, raised errors, hosted
  inline mode, Ctrl-C, resize, split descriptors, and the editor example.
- Package compilation passes with `--Werror`; formatting and strict-type checks
  pass.
- The unsafe audit finds nine documented FFI calls in the single allowlisted
  file `mojotui/platform/posix.mojo`.
- CI runs the locked check on Linux x86-64, Linux ARM64, and macOS ARM64.
- The tag workflow repeats that matrix before creating a source archive.
- Stages A through H and the editor dogfood milestone are implemented. Stage I
  is open. Stage J is deferred until the extension boundary is stable.

The baseline is green, but the current imports are not yet a distributable
dependency DAG:

- `core.cell` imports `text.width`, while `text.rich` imports `core`.
- `terminal.backend` imports the POSIX `platform` package, so headless terminal
  consumers inherit a platform dependency.
- `editor` combines the document engine, terminal widget, keymap integration,
  filesystem service, and POSIX atomic replacement.

Those couplings are release work, not undocumented exceptions.

## Target dependency graph

Before changing package, frame, backend, event, or application-host boundaries,
read the [pinned reference architecture](reference-architecture.md) for the
adopted and rejected upstream patterns that constrain this graph.

MTUI-002 may refine names, but it must preserve this direction:

```text
private Unicode-width kernel
            |
            v
           core <--------- text
            |               |
            +-------> widgets
            |               |
            +-------> terminal-core
            |               |
private POSIX boundary ---> terminal-posix
            |               |
            +-------> event-+
                            |
                            v
                           app

core + text ------------> editor-engine
widgets + editor-engine -> editor-widget
event + app ------------> editor-controllers
private POSIX boundary -> editor-file-service
editor-widget + widgets -> forms

all public packages ----> mojotui convenience imports
```

The distribution remains one independently installable `mojotui` library
unless MTUI-001 records a different decision. “Packages” in this plan means
public Mojo import boundaries inside that distribution. A consumer importing
the headless core must not compile or link the POSIX boundary.

## Milestones and issues

Each issue should produce one reviewable PR. Split an issue if its diff crosses
two ownership lanes or cannot be reviewed independently.

### M0 — Freeze the release contract

#### MTUI-001 — Reconcile release numbering and scope

Depends on: none.

Status: implemented in draft PR
[#4](https://github.com/Ameyanagi/mojotui/pull/4); complete when that PR merges.

Update the version, release, stability, and changelog documents so they agree
that `v0.1.0` is the first public release. Preserve the history of completed
Stages A–H; do not relabel implemented work as new. Record whether the single
distribution contains multiple public subpackages or whether multiple artifacts
are required.

Completion criteria:

- `pixi.toml`, `CHANGELOG.md`, `PLAN.md`, `docs/stability.md`, and the release
  workflow name one release and one compiler compatibility policy.
- The Stage I requirements assigned to `v0.1.0` and the Stage J post-release
  backlog are explicit.
- `pixi run --locked check` passes.

#### MTUI-002 — Specify and enforce import boundaries

Depends on: MTUI-001.

Write the authoritative package DAG and add a non-mutating import-boundary
check to `pixi run lint`. Cover public and private packages, permitted edges,
and the convenience root. The check must report the importing file and forbidden
edge.

Completion criteria:

- The checked graph accounts for every cross-package import under `mojotui/`.
- A test fixture proves the check fails on a forbidden reverse edge.
- The current `core`/`text`, terminal/POSIX, and editor couplings are either
  rejected or listed as temporary violations owned by MTUI-101 through
  MTUI-103.
- `pixi run --locked check` passes.

#### MTUI-003 — Capture release baselines

Depends on: MTUI-001.

Run the locked suite and both checked-in benchmarks from a clean tree. Record
the compiler, Pixi version, CPU, OS, command lines, iteration policy, medians,
and commit. This is regression evidence, not a performance claim.

Completion criteria:

- Test counts, PTY cases, unsafe-call count, and benchmark methodology are
  reproducible from the record.
- `git status --short` is empty after the run, excluding the intended record.
- No timing threshold is added to heterogeneous CI runners.

### M1 — Establish dependency-directed packages

#### MTUI-101 — Break the `core`/`text` cycle

Depends on: MTUI-002.

Move the Unicode-width kernel to a leaf that `Cell` can use without importing
the rich-text package. Keep public width functions available from
`mojotui.text`; do not duplicate generated tables or width policy.

Completion criteria:

- `core` has no import edge to the public `text` package.
- Existing grapheme, emoji, CJK, ambiguous-width, and wide-cell invariant tests
  pass unchanged or with mechanical import updates.
- Unicode version and generation provenance have one source of truth.
- The import-boundary check and `pixi run --locked check` pass.

#### MTUI-102 — Separate headless terminal code from POSIX terminal code

Depends on: MTUI-002; may run in parallel with MTUI-101.

Keep frame transactions, patches, the backend trait, and the headless backend
usable without POSIX. Move descriptor sizing, sessions, ANSI/inline descriptor
output, and environment detection behind the POSIX terminal package.

Completion criteria:

- A compile smoke test imports the headless terminal surface without importing
  `mojotui.platform`.
- ANSI, inline, resize, split-descriptor, cursor, and restoration tests remain
  green.
- No FFI call is added and the unsafe allowlist remains one file.
- The import-boundary check and `pixi run --locked check` pass.

#### MTUI-103 — Separate editor engine, integrations, and services

Depends on: MTUI-002; may run in parallel with MTUI-101 and MTUI-102.

Make document, selection, history, commands, and highlight state a terminal-free
editor engine. Keep widget rendering, controller keymaps, clipboard providers,
and POSIX file replacement in outward layers. Preserve the documented top-level
convenience imports.

Completion criteria:

- A compile smoke test imports and edits a document through the approved
  editor-engine subpackage without terminal, event, app, widgets, or platform
  imports.
- Editor widget, forms, controller, file-service, headless example, and PTY
  tests pass.
- Public replacements and any moved imports are recorded in migration notes.
- The import-boundary check and `pixi run --locked check` pass.

#### MTUI-104 — Prove the public subpackage surface

Depends on: MTUI-101, MTUI-102, MTUI-103.

Add compile/run fixtures that consume each supported subpackage and the
`mojotui` convenience root using only public imports. Audit every root export;
remove accidental internals and add missing supported names deliberately.

Completion criteria:

- Fixtures cover core/headless rendering, widgets, POSIX terminal setup,
  application hosting, editor engine, editor widget, and forms.
- Every documented import compiles on the pinned nightly.
- Compile-fail coverage protects at least one private boundary.
- `pixi run --locked check` passes.

### M2 — Ship the extension foundation

#### MTUI-201 — Add validated symbol sets

Depends on: MTUI-101.

Add public border, line, bar, scrollbar, shade, and braille symbol values with
validated construction. Keep width-sensitive symbols explicit and reject
invalid multi-column choices where the renderer requires one cell.

Completion criteria:

- Unit tests cover built-in sets, custom valid sets, invalid widths, and wide
  grapheme boundaries.
- Widgets no longer hide duplicated symbol constants that callers need to
  replace.
- New semantic values follow the nominal-type and compile-fail policies.
- `pixi run --locked check` passes.

#### MTUI-202 — Migrate existing widgets to public symbols

Depends on: MTUI-201.

Adopt the public symbol sets in Block, Gauge, LineGauge, Scrollbar, Sparkline,
List, Table, Tabs, and Fill without changing default snapshots.

Completion criteria:

- Existing default golden output is unchanged.
- Focused snapshots cover one custom symbol set per affected widget family.
- Invalid public configuration is rejected rather than normalized.
- `pixi run --locked check` passes.

#### MTUI-203 — Publish a headless extension test kit

Depends on: MTUI-101; may run in parallel with MTUI-201.

Expose stable buffer snapshot formatting, golden comparison helpers, and a
wide-grapheme invariant assertion through a public test-support package. Keep
the helpers deterministic and free of terminal I/O.

Completion criteria:

- The test kit detects orphan leaders, orphan continuations, and snapshot
  mismatches with actionable messages.
- Its own tests include ASCII, combining text, CJK, emoji, clipping, and
  overlays.
- A consumer fixture imports only the core and test-support surfaces.
- `pixi run --locked check` passes.

#### MTUI-204 — Add a third-party widget template

Depends on: MTUI-104, MTUI-201, MTUI-203.

Add a standalone example package that implements a custom widget, configures a
symbol set, renders headlessly, and asserts a golden snapshot. It must use no
private Mojotui name.

Completion criteria:

- The example builds and runs as part of the locked suite.
- Copying the example outside the repository requires only documented public
  imports.
- The custom-widget guide links to the example and explains stateless and
  stateful ownership.
- `pixi run --locked check` passes.

#### MTUI-205 — Normalize builders and decide `Terminal.draw()`

Depends on: MTUI-104.

Inventory public fluent configuration, adopt consistent `with_*` builders for
the supported surface, and test ownership behavior. Implement a closure-based
`Terminal.draw()` only if a minimal compile experiment proves the borrow ends
before presentation and errors cannot commit a partial frame. Otherwise record
the compiler limitation and keep `begin_frame`/`finish_frame` canonical.

Completion criteria:

- The inventory accounts for every supported public configurable value.
- Builder chains have focused ownership and behavior tests.
- The draw decision includes compiling evidence and one documented canonical
  render pattern.
- Breaking renames have migration entries and compile fixtures where useful.
- `pixi run --locked check` passes.

#### MTUI-206 — Make Ratatui fixtures reproducible

Depends on: MTUI-002; may run in parallel with the other M2 work.

Regenerate shared layout fixtures from published tag `ratatui-v0.30.2`, peeled
commit `e665c36cb14752a61cd777fbd06dbef8474f2add`. Check in generator version,
inputs, output checksum, and license/provenance notes. Ratatui remains a
development input, not a runtime dependency.

Completion criteria:

- A clean regeneration reproduces the checked checksum byte-for-byte.
- The corpus covers every shared constraint, flex, spacing, margin, priority,
  and rounding case claimed in `docs/layout-compatibility.md`.
- Observable differences are either fixed or documented as deliberate API
  exclusions.
- `pixi run --locked check` passes.

### M3 — Package and release

#### MTUI-301 — Add the installable package recipe

Depends on: MTUI-104.

Add `conda.recipe/recipe.yaml` and a deterministic package task. Pin the Mojo
compiler compatibility required by the precompiled package and install under
the standard prefix Mojo library directory. Keep Python, Rust, C, and ncurses
out of runtime dependencies.

Completion criteria:

- A clean recipe build produces one `mojotui` artifact from the tagged source
  layout.
- A fresh prefix imports core, widgets, and the convenience root without
  `-I` paths into the checkout.
- A POSIX consumer smoke test runs on every supported target.
- Recipe tests fail if the installed artifact accidentally reads source files
  from the repository.

#### MTUI-302 — Extend CI with consumer and package gates

Depends on: MTUI-301.

Keep the existing three-target locked check and add installed-consumer coverage.
Build the package once per target unless artifact portability is proven. Use
least-privilege workflow permissions and retain fail-fast false for the platform
matrix.

Completion criteria:

- Pull requests run source validation and installed-consumer smoke tests.
- The release workflow consumes the same checked task definitions as CI.
- Dependency caches cannot substitute an untested checkout for the installed
  artifact.
- All matrix jobs pass at one commit.

#### MTUI-303 — Complete the release documentation

Depends on: MTUI-204, MTUI-205, MTUI-301.

Audit the quick start, API map, architecture, backends, terminals, custom
widgets, editor guide, stability tiers, limitations, migration notes, security
policy, and changelog against the installed artifact. Prefer executable snippets
over duplicate reference tables.

Completion criteria:

- A new consumer can install, render headlessly, run an application, and test a
  custom widget using only documented commands.
- Every documented public name is covered by MTUI-104 or MTUI-204.
- Experimental app/editor/form surfaces and unsupported Windows/runtime cases
  are prominent.
- Prose is checked with the `unslop` workflow and `pixi run --locked check`
  passes.

#### MTUI-304 — Run the release candidate gate

Depends on: MTUI-202, MTUI-203, MTUI-206, MTUI-302, MTUI-303.

Cut an immutable release-candidate commit without tagging it. Run source,
package, consumer, PTY, compile-fail, unsafe, and benchmark checks from clean
worktrees. Exercise the source archive produced by the release workflow.

Completion criteria:

- Linux x86-64, Linux ARM64, and macOS ARM64 pass at the same commit.
- The source archive and package install into fresh directories and pass public
  API smoke tests.
- Full, one-cell, unchanged-frame, and 10 MiB editor benchmark medians are
  recorded; a repeated material regression is resolved or accepted explicitly.
- `CHANGELOG.md` contains no placeholder release claims.

#### MTUI-305 — Publish `v0.1.0`

Depends on: MTUI-304. Maintainer authorization required.

Create the signed or annotated tag from the approved release-candidate commit,
let the release workflow build the source release, publish the package only if
MTUI-301 and MTUI-302 passed, and verify the public assets from fresh prefixes.

Completion criteria:

- The tag resolves to the approved commit and the GitHub release is public.
- The protected `release` environment records approval by a designated
  maintainer after that reviewer verifies the peeled tag target.
- Checksums, source archive, compatibility statement, changelog, and install
  command agree.
- A clean consumer can reproduce the quick start.
- Follow-up defects are filed; the release commit is not rewritten.

## Parallel execution

Use one Git worktree per agent. Never run two implementation agents in the same
worktree. A suggested layout is
`/Users/ryuichi/dev/worktrees/mojotui/<issue-id>` with branch names
`agent/<issue-id>-<short-name>`.

```text
Wave 0: MTUI-001 -> MTUI-002
                    |
Wave 1:     +-------+-------+----------------+
            |               |                |
         MTUI-101        MTUI-102         MTUI-103
            |               |                |
            +---------------+----------------+
                            |
                         MTUI-104

Wave 2: MTUI-201 -> MTUI-202
        MTUI-203 ---------> MTUI-204
        MTUI-205
        MTUI-206

Wave 3: MTUI-301 -> MTUI-302
        MTUI-204 + MTUI-205 + MTUI-301 -> MTUI-303
        all required M2/M3 work -> MTUI-304 -> MTUI-305
```

Within a wave, assign non-overlapping ownership:

- boundary agents own package roots, import checks, and their focused tests;
- symbol agents own symbol values and widget migration;
- test-kit agents own public test support and the external example;
- fixture agents own generator inputs, corpus output, and provenance;
- release agents own recipes, workflows, release docs, and artifact smoke tests.

If two tasks need the same public `__init__.mojo`, the first PR lands before the
second rebases. Do not resolve export conflicts by exposing both alternatives.

## Verification gates

Every PR runs the smallest focused test during development and ends with
`pixi run --locked check`. Additional gates are cumulative:

| Gate | Required evidence |
| --- | --- |
| G0 baseline | 217 tests, 29 modules, 20 compile-fail fixtures, PTY pass, 9 allowlisted FFI calls |
| G1 boundaries | import-DAG check, headless-without-POSIX smoke, editor-engine-only smoke |
| G2 extensions | symbol validation, test-kit self-tests, third-party widget public-import test |
| G3 packaging | clean recipe build and fresh-prefix consumer tests on all supported targets |
| G4 release | one commit green across source, package, PTY, safety, API, archive, and benchmark evidence |

Performance PRs compare at least five interleaved baseline/candidate runs on the
same idle host. Retain a change only when semantic tests pass and the improvement
survives a second run. CI reports benchmarks but does not use cross-machine
timings as pass/fail thresholds.

## Agent and PR workflow

For each issue:

1. Read `AGENTS.md`, this plan, and the subsystem document linked by the issue.
   Confirm a clean, issue-specific worktree and record the base commit.
2. Inspect the owning source and tests. For behavior changes, add a focused red
   test before implementation. For structural changes, add the boundary smoke
   test first.
3. Implement only the issue's acceptance criteria. Preserve deterministic
   rendering, strict types, explicit effects, and the zero-default unsafe budget.
4. Run focused tests, then `pixi run --locked check`. Record exact commands and
   relevant counts in the PR.
5. Apply `writing-for-agents` to agent-facing docs and `unslop` to user-facing
   prose. Keep one source of truth; link to architecture references instead of
   copying them.
6. Use `file-pr` only after the complete branch diff and validation are ready.
   It must file one real PR and include compatibility, safety, and performance
   impact.
7. Use `babysit-pr` to verify review findings, fix confirmed code failures, and
   continue until required checks and legitimate threads are resolved. Merging
   remains a maintainer action.
8. At a session boundary, use `handoff`; it writes to the OS temporary directory
   and links this plan, the issue, PR, and commit instead of duplicating them.
9. Use `agent-history-audit` only after recurring workflow failures are observed;
   propose instruction changes with evidence and wait for approval before
   editing agent policy.

Use `grilling` before implementation only when MTUI-001 or a later public API
decision is reopened by the maintainer. It is an interactive decision workflow,
not a substitute for repository research.

## Handoff template

Every agent handoff must provide:

```text
Issue:
Worktree and branch:
Base and HEAD commits:
Files intentionally changed:
Public API or compatibility effect:
Tests added or changed:
Commands run and results:
Benchmark evidence, if applicable:
Unsafe/FFI effect:
Open review threads or blockers:
Next dependency unlocked:
Suggested skills for the next session:
```

The receiving agent verifies the branch, diff, and commands rather than trusting
the summary. A handoff is complete when the next agent can identify the exact
remaining acceptance criterion without reading the prior conversation.

## Risks and responses

| Risk | Response |
| --- | --- |
| Package splitting creates import cycles | Land MTUI-002 first; make the DAG executable and remove cycles one subsystem at a time. |
| A headless import still links POSIX | Require a consumer fixture that imports only headless packages and inspect its dependency boundary. |
| Mojo nightly breaks builders or closures | Keep the exact nightly pinned; gate `Terminal.draw()` on a minimal ownership experiment. |
| Precompiled artifacts are compiler-incompatible | Pin compiler compatibility and test from fresh prefixes on every supported target. |
| Public symbols break default snapshots | Separate symbol definitions from widget migration and require unchanged default goldens. |
| Generated Ratatui fixtures drift | Pin tag, peeled commit, generator version, and checksum; regenerate in a clean directory. |
| Parallel agents collide on exports | Use separate worktrees and serialize PRs that touch the same package root. |
| Unsafe code spreads during packaging or optimization | Keep the existing allowlist check in every gate; new unsafe work requires a separate reviewed issue. |
| Documentation outruns the API | Compile every documented import through consumer fixtures before release. |
| A release workflow publishes an unverified artifact | Make publication depend on the same matrix and installed-consumer tasks used by pull requests. |

## Explicit non-goals for v0.1

- Windows terminal support
- A concrete adapter for private Mojo AsyncRT APIs
- Rust or Ratatui source compatibility
- BarChart, Chart, Canvas, GPU rendering, or SIMD diffing
- A general constraint solver, negative layout spacing, or CSS grid
- Native clipboard reads or persistent undo history
- Syntax grammar, language-server, completion, or diagnostics implementations
- Python, Rust, C, ncurses, or another runtime dependency for consumers
- Cross-machine benchmark rankings or performance-superiority claims
- A stable 1.0 compatibility promise for `event`, `app`, `editor`, or `forms`

## Post-v0.1 backlog

Stage J begins only after public extension consumers validate the Stage I
surface. Create separate milestones for deeper existing widgets, then BarChart,
then Chart, then visible-viewport text and collection work. Canvas and GPU work
remain deferred. Each optimization starts from a checked benchmark, keeps a
scalar reference path, adds semantic equivalence tests, and earns retention with
reproducible end-to-end evidence.

## Definition of done

`v0.1.0` is ready when MTUI-001 through MTUI-304 are complete, the supported
subpackage graph is acyclic and machine-checked, a third-party widget builds and
tests without private imports, the package works from fresh prefixes on all
three supported targets, release documentation matches the installed artifact,
and the release-candidate commit passes G4 without expanding the unsafe
boundary. Publication occurs only through MTUI-305 with maintainer approval.
